# Deploy Vegan API with GitHub Actions and Coolify

## Release pipeline

The existing `.github/workflows/verify.yml` now runs **Build & Deploy**:

1. Verify: clean install on Node 24, formatting, `npm run build`, offline tests, production dependency audit, isolated MongoDB replica-set tests and Docker build.
2. Build & Push: publish AMD64/ARM64 images to `ghcr.io/mma-superorganization/vegan-api` with `latest` and `sha-<full commit SHA>` tags.
3. Deploy: send an authenticated GET request to the Coolify resource webhook after the image push succeeds. Missing secrets, HTTP errors and connection timeouts fail this job.

Pull requests and pushes to other branches only verify. Pushes to `main` publish and deploy. You can also select **Actions → Build & Deploy → Run workflow → main** to rerun a release after configuring secrets. Main releases are serialized. A successful webhook call means Coolify accepted the request; confirm the deployment and readiness in Coolify separately.

## GitHub configuration

Open **Settings → Secrets and variables → Actions → New repository secret**:

| Secret                | Value                                                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `COOLIFY_WEBHOOK_URL` | HTTPS **Deploy Webhook (auth required)** URL for this backend resource, copied from Coolify's **Configuration → Webhooks**. |
| `COOLIFY_TOKEN`       | Coolify API token with `deploy` permission for the resource's team.                                                         |

`GITHUB_TOKEN` is generated by Actions; do not create it manually. The publishing job requests `packages: write`. Organization/package policy must permit this repository to publish its package. If a package already exists, grant this repository Actions access in the package settings.

Application credentials belong in Coolify runtime variables, not GitHub build arguments. The Docker image excludes `.env` and uses `node src/server.js`.

## Coolify resource

Create a **Docker Image** application on the deployment server. Set:

| Setting          | Value                                     |
| ---------------- | ----------------------------------------- |
| Docker image     | `ghcr.io/mma-superorganization/vegan-api` |
| Image tag        | `latest`                                  |
| Port exposed     | `3000`                                    |
| Domain           | Your backend HTTPS domain                 |
| Healthcheck path | `/api/v1/health/ready`                    |
| Healthcheck port | `3000`                                    |

Use the application's existing Docker readiness check, or configure the equivalent HTTP check above. If you change `API_PREFIX` or `PORT`, update the Coolify check too. The container starts with the Dockerfile's command; leave the command override empty. This resource pulls the published image, so do not configure source rebuilding or a separate Git auto-deploy for it.

For a private GHCR package, authenticate Docker on each deployment server as the server user used by Coolify. Use a GitHub account with package access and a token with `read:packages`; enter the token privately through `docker login ghcr.io --username YOUR_GITHUB_USERNAME`. This pull credential is separate from the Coolify deploy token and the workflow's temporary `GITHUB_TOKEN`.

On self-hosted Coolify, enable API access in Settings if disabled. Create the deploy token under **Keys & Tokens → API Tokens**. Copy the resource's authenticated deploy webhook into the repository secret above.

## Runtime environment

Add runtime variables in Coolify (not build-time variables). Do not paste JSON field quotes into email/project ID values.

```dotenv
NODE_ENV=production
PORT=3000
API_PREFIX=/api/v1
APP_BASE_URL=https://YOUR_BACKEND_DOMAIN
LOG_LEVEL=info
SWAGGER_ENABLED=false
TRUST_PROXY=0

MONGODB_URI=YOUR_ATLAS_OR_REPLICA_SET_URI
MONGODB_DB_NAME=vegan_support
FIREBASE_PROJECT_ID=YOUR_PROJECT_ID
FIREBASE_CLIENT_EMAIL=YOUR_SERVICE_ACCOUNT_EMAIL
FIREBASE_PRIVATE_KEY=YOUR_COMPLETE_PEM_PRIVATE_KEY
CLOUDFLARE_R2_ACCOUNT_ID=YOUR_ACCOUNT_ID
CLOUDFLARE_R2_ACCESS_KEY_ID=YOUR_ACCESS_KEY
CLOUDFLARE_R2_SECRET_ACCESS_KEY=YOUR_SECRET_KEY
CLOUDFLARE_R2_BUCKET_NAME=YOUR_PRIVATE_BUCKET

AI_ENABLED=false
FCM_ENABLED=false
REMINDER_SCHEDULER_ENABLED=false
```

The example placeholders must be replaced before startup. For `FIREBASE_PRIVATE_KEY`, supply the complete PEM value with actual newlines or literal `\n`; the application normalizes escaped newlines. Set `CORS_ORIGINS` to required browser origins. Set `TRUST_PROXY` for the actual proxy chain or trusted proxy addresses; `0` is the conservative default. Only use `1` when all traffic reaches the app through exactly one trusted proxy and direct container access is blocked.

Enable Firebase Authentication and its sign-in providers. Permit the deployment server in Atlas network access and use a replica-set connection for transactions. Production does not auto-build indexes: provision reviewed indexes using `npm run db:indexes` in an authorized environment before serving traffic. Never configure automatic seed/migration execution as the container startup command.

AI, FCM and reminder polling stay disabled unless explicitly enabled with their required configuration. See the [environment contract](../README.md#environment-contract-all-47-keys) for optional values. Keep one scheduler instance when polling is enabled.

## First deployment and rollback

1. Configure the Coolify resource, registry pull access, runtime variables and both GitHub secrets.
2. Push to `main` or manually run the workflow on `main`.
3. Confirm Verify and Build & Push pass, then check the matching Coolify deployment logs.
4. Check `/api/v1/health/ready` on the deployed domain. Health alone does not verify login, media uploads or AI calls; validate enabled providers using the staging acceptance workflow.

For rollback, set the Coolify image tag to a previously verified `sha-<full commit SHA>` and redeploy. Automatic deployments use whichever tag the resource is configured to pull: return it to `latest` when resuming the normal release flow. Keep the SHA images you need for rollback in GHCR. Database compatibility and backups must be assessed separately from image rollback.
